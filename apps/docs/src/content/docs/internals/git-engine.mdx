---
title: The git engine
description: Phased clones in a dedicated facet — network fetch, indexing, and a chunked, resumable checkout.
---

`git clone` is the hardest single command in the machine: it's
network-heavy, CPU-heavy (pack indexing), and write-heavy (checkout), three
different resource profiles that would each blow a single isolate's budget
on a big repository. So the git engine runs in a **dedicated facet** and
treats the clone as phases, each with a fresh CPU budget.

## The phases

1. **Clone-prepare / fetch**: negotiate over HTTPS with the remote, stream
   the packfile.
2. **Index**: index pack objects so checkout can address them.
3. **Chunked checkout**: materialize the worktree in bounded, resumable
   slices via **bounded continuation**. Each slice stays inside its
   invocation budget and hands a continuation to the next, so worktree size
   is bounded by the disk, not by any single isolate's CPU or memory.

Checkout writes stream to the supervisor through the same
credit-backpressured pipeline as everything else
([inside the disk](/docs/internals/disk/)), so an 84,000-file checkout
cannot flood the DO.

## Measured behavior

| Repository | Result |
|---|---|
| facebook/react — 7,300 files | ~28 s |
| 84,000-file worktrees | materialize via bounded continuation |

The engine's correctness is unit-tested at the protocol and checkout layers
(`tests/unit/git-network-facet-*.mjs`, `cf-git-*.mjs`: clone protocol,
closed-world behavior, checkout repairs, large reads, checkout performance).

## The honest ceiling

Fetch-side **index-pack CPU headroom for 75,000+-object clones** is still in
progress: on repositories like microsoft/TypeScript the indexing phase can
exceed a per-invocation CPU budget. Continuation-slicing the indexer the way
checkout was sliced is the known path
([research frontier](/docs/fine-print/research/)).
