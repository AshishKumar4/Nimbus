The filesystem is a purpose-built VFS over the Durable Object's SQLite
storage (`packages/worker/src/vfs/sqlite-vfs.ts`). It is the single source
of truth for every byte in the session.

## Storage model

- **Inodes** live in a SQLite table (`path`, `parent_path`, `kind`, `size`,
  times, `mode`, `chunk_count`, `content_id`) with the full inode map held
  resident in memory — path resolution and permission-style checks are Map
  lookups, not queries.
- **File contents are chunked** (64 KiB chunks) with an LRU content cache in
  front. Range reads and writes touch only the chunks a range covers —
  never whole-file rewrites.
- **Content generations**: bulk writes stage into a bounded generation and
  **publish atomically** — a crashed install can't leave a half-written
  tree visible.
- **Durability**: batch writes are synchronously durable; `fsync` and
  process exit are durability boundaries. Hibernation never loses committed
  writes.
- **The mode column is real**: `chmod` persists durable modes (and the exec
  bit that `./prog` dispatch honors), bumping the revision watermark like
  any other mutation.

## Revisions — precise cache invalidation

Every path carries a **subtree revision watermark**: it changes iff that
path or anything under it mutated. Runtime caches (Node's fs snapshot,
prefetch surfaces, page caches) key on it, so an unrelated write elsewhere
in the tree doesn't invalidate your cache — and a stale cache can't survive
a real change. A VFS event bus streams mutation events, coalesced for the
browser file-watcher and used for runtime invalidation.

## The write path — credit backpressure

Facets mutate the disk only through the supervisor's streaming write RPC,
governed by a **credit pool**: a facet must hold credits to send bytes, and
credits are returned as the supervisor drains. The result is a hard bound on
supervisor memory no matter how many processes write at once — the
mechanism that lets a parallel `npm install` (52,500 files) or an
84,000-file git checkout land safely inside a 128 MB isolate.

## The read path — bridge + caches

The runtime filesystem contract is `RuntimeFsBridge`
(`packages/worker/src/runtime/os-contracts.ts`): `stat`, `readFile`,
`readRange`/`writeRange`/`truncate` (stateless — correct across supervisor
hibernation because no server-side handle state exists), directory and
symlink operations, `revision(path)`, and event subscription.

How runtimes consume it, honestly:

- **Node async fs** (`fs.promises`, `FileHandle` positional I/O, truncate,
  live appends) rides the live bridge, including files created by child
  processes after a facet started.
- **Node sync fs** serves from a bounded startup snapshot plus a local
  write cache — a documented synchronous optimization, invalidated by
  revisions.
- **Python, Ruby, and WASI one-shots** use bounded snapshot + diff-flush —
  acceptable for short commands; migrating their long-running I/O onto the
  live bridge is active work
  ([research frontier](/docs/fine-print/research/)).

The coherence rule the design converges on: every read observes either the
latest committed VFS revision or the reader's own unflushed write; stale
writes conflict deterministically and loudly, never by silent overwrite.

## Design rules (from the OS spec)

- No per-byte Durable Object RPC — 64 KiB pages or better.
- No unbounded whole-tree snapshots for long-running processes.
- Binary data travels as bytes (`Uint8Array`/streams), never JSON envelopes.
- Bounded dirty caches with high-water flushing.
