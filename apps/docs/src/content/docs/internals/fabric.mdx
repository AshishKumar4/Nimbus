This is the deep-dive section. Each page covers one subsystem; this one is
the map.

## The shape

One session is one Cloudflare Durable Object (the supervisor) plus a fabric
of Worker Loader isolates (facets).

<FabricDiagram />

The division of labor is strict:

- The supervisor owns all durable state: the SQLite-backed filesystem, the
  shell, the process table, the port registry, and the session agent. It is
  the only thing that must survive; everything else is rebuildable.
- Facets own all heavy compute. Every process runs in its own facet isolate
  with its own memory and CPU budget: one-shot facets for commands,
  resident keyed facets for servers, and a dedicated git engine.
- The platform owns cross-session state. npm tarballs, runtime blobs, and
  staged app bundles live in R2, with hot reads cached at the per-colo
  edge, and big npm installs fan out across peer DOs.

## Why this shape

Two platform facts force the design:

1. Isolates are capped. Cloudflare publishes 128 MB per isolate, plus
   per-invocation CPU budgets. Running user workloads inside the supervisor
   would make the OS compete with its own processes for one budget. So the
   supervisor schedules and facets compute.
2. Durable Objects are the only durable, strongly-consistent home. Facet
   state is evictable at any time, so anything worth keeping streams back
   to the supervisor, and anything in a facet is treated as
   reconstructible.

The payoff is the OS move: since each process already lives in its own
isolate, a heavy app can span several. That's how opencode runs as a serve
plus TUI pair, each with its own budget, joined by loopback.

## One request, end to end

What happens when a process curls a server in another isolate:

1. `curl http://127.0.0.1:4096/doc` runs in facet B. The loopback address
   is session-internal; the shim forwards the request to the supervisor.
2. The supervisor's port registry looks up port 4096, finds the resident
   facet A that registered it, and routes the `Request` through A's route
   stub.
3. Facet A's HTTP shim dispatches to the server the app actually started.
   The `Response` streams back through the relay; bodies are piped live,
   never buffered to completion
   ([ports & routing](/docs/internals/network/)).

The browser preview at `/s/<id>/port/4096/` takes the exact same path from
step 2. The fabric makes no distinction between internal and preview
ingress.

## Writes flow one way

Facets never own files. Every filesystem mutation streams back to the
supervisor through a credit-backpressured write pipeline. The facet must
hold credits to send, so a parallel `npm install` or an 84,000-file
checkout physically cannot flood the supervisor's memory
([inside the disk](/docs/internals/disk/)).

## Failure, plainly

- Facet isolates can be evicted under memory pressure; module-scope state
  simply vanishes between calls. The process table on the DO side stays
  authoritative, and a process that can't be rehydrated is marked dead with
  a reason.
- Heavy staging (opencode's ~20 MB module map, for example) is assembled
  outside the supervisor's isolate on the Worker-Loader cache-miss path, so
  staging a big app can't OOM the DO that owns your files.
