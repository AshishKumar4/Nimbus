Every process runs in its own isolate. The 128 MiB per-isolate limit and
per-invocation CPU budgets are Cloudflare's published figures. Durable
Objects are the only durable, strongly consistent primitive on the
platform, so the supervisor owns the disk, shell, process table, and port
registry. Facets do the work and can be evicted.

An app can span several isolates. That's how opencode runs as a server and
TUI joined by loopback, with a separate budget for each half.

## Why a Durable Object

Workers are stateless and can run anywhere; a sandbox needs one place
where the working directory, the process table, and the disk agree. A
Durable Object is the only Cloudflare primitive that is both durable and
strongly consistent: a single-threaded actor with transactional SQLite
storage attached. One session is exactly one DO instance, addressed by
`tenant:sessionId`. There is one instance per session and no replicas, so
there is no cache-coherence protocol to run.

The supervisor holds, in one actor:

- **The disk** — the SQLite-backed VFS, 10 GB, the single source of
  truth for every byte ([inside the disk](/docs/internals/disk/)).
- **The process table** — pid-keyed state that survives facet resets;
  `ps` reads the DO, never a facet. Each process carries an immutable
  credential (uid, gid, groups, umask) assigned at spawn.
- **The port registry** — which pid owns which port, and the facet stub
  that serves it ([ports & routing](/docs/internals/network/)).
- **Per-process log ring buffers and input queues** — durable and
  bounded, so `logs <pid>` works after a facet dies.
- **Hibernatable WebSockets** — terminals survive DO eviction, and
  configured auto-responses answer idle pings without waking the actor.

The supervisor enforces a soft heap ceiling on itself of 64 MiB, half the
platform cap. A supervisor OOM resets the whole session rather than failing
a single process, so heavy work is pushed out to facets.

## Facets: the Worker Loader fabric

Facets are dynamically loaded Workers created through the platform's
Worker Loader binding. Each gets the standard `nodejs_compat` runtime, a
128 MiB heap of its own, and exactly one injected capability: a
`SUPERVISOR` RPC stub pointing back at its own session. Generated facet
code cannot import supervisor modules — the RPC surface is the whole
contract.

The loader keys isolates by content hash and slot, so repeated runs of
the same program reuse a warm isolate instead of re-instantiating. Warm
reuse also sets the failure rule: a route stub for an evicted facet fails
loudly rather than re-loading the code, because a re-loaded isolate is an
empty worker with nothing listening.

The supervisor describes a big app with a small spec — argv, env, a
bounded VFS snapshot — and the full module map is assembled outside the
DO, in a stateless isolate on the loader's cache-miss path. opencode's map
is roughly 20 MB. Assembling it inside the supervisor crossed the memory
cap and reset the session, so assembly runs outside the DO.

<RequestLifecycle caption="A preview request and an in-session curl take the same path through the registry, and the response streams the whole way." />

Writes flow one way. Facets never own files. Every mutation streams to the
supervisor through a credit pool, so a parallel `npm install` can't flood the
DO ([inside the disk](/docs/internals/disk/) has the numbers).

## Peers: a second memory envelope

Every process runs in a facet, minted by some DO's `env.LOADER`. A local
facet comes from the coordinator session DO and shares its workerd memory
envelope. A peer facet comes from a sibling DO and gets its own 128 MiB
budget, so it runs in parallel with the coordinator and with every other
peer.

Peers are session DOs in the same `NIMBUS_SESSION` namespace as the
coordinator, named `${coordinatorDoId}:proc:${slot}`, so they need no
extra Worker, binding, or configuration. A heavy spawn fails loudly when
that namespace is missing. The npm resolve fan-out uses the same pattern
for short-lived batch work: a fan-out of five or more shards runs on
`nbf:`-prefixed siblings, up to 32 of them.

Eight peers hold about 150 MiB each at the same time, 1.2 GiB across one
session. A peer that runs out of memory takes down its own process,
leaving the siblings and the coordinator running.

One process class is heavy today: the opencode attach TUI, which is
resident, memory-growing, and serves no inbound HTTP. A heavy spawn pays
about 0.5 s of peer cold-create. Everything that binds a port stays
local.

<PeerFacet caption="A peer facet is minted with the coordinator's doId in its SUPERVISOR props, so its filesystem, terminal, and port calls land on the coordinator, not on the DO it runs in." />

The `SUPERVISOR` binding a facet receives carries a `doId` in its props,
and the RPC layer resolves that doId to a stub on every call. A facet
booted on a peer is minted with the *coordinator's* doId, so `readFile`,
`writeFile`, stdout and stderr frames, the stdin pump, and `registerPort`
all land on the coordinator, exactly as they do for a local facet. The
peer lends a loader and a memory budget; the disk, the terminal, and the
ports stay where they are.

## Inbound HTTP stays local

The Workers runtime will not re-enter a peer-hosted facet to serve an
inbound request. Processes that bind a port therefore run on the
coordinator: `node`, `vite`, `wrangler`, Python, Ruby, and opencode in
server mode, whose readiness gate polls `/doc` back through the same
router. Each launch primitive declares its class, and one policy point
reads it.

## Design constraints

| Constraint | Cloudflare's figure | What it produced |
|---|---|---|
| Isolate memory | 128 MiB each | multi-isolate processes; staged module maps; peer DOs for heavy residents |
| DO SQLite storage | 10 GB per object | the session disk |
| CPU per invocation | 30 s default, 5 min via `limits.cpu_ms` | phased git clone, sliced checkout, fan-out installs |

A raised `cpu_ms` applies to the supervisor. Facets keep ~30 s, so long
facet work must be split into phases. When the DO hibernates, its disk stays.

## Trust

Nimbus inherits workerd's isolation, the same primitives Cloudflare runs
untrusted customer code on. The CSP allows no runtime `eval` and no
request-time WASM compilation. Sessions share only read-only,
content-addressed caches, and loopback stays inside a session.
[Security](/docs/internals/security/) covers the full model — isolation,
Unix permissions, tokens — and its current gaps.
