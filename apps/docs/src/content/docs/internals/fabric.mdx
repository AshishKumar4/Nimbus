I run every process in its own isolate because the platform gives me
nothing else. The 128 MiB per-isolate limit and per-invocation CPU budgets
are Cloudflare's published figures. Durable Objects are the only durable,
strongly consistent home. The supervisor owns the disk, shell, process table,
and port registry. Facets do the work and can be evicted.

An app can span several isolates. That's how opencode runs as a server and
TUI joined by loopback, with a separate budget for each half.

<RequestLifecycle caption="A preview request and an in-session curl take the same path through the registry, and the response streams the whole way." />

Writes flow one way. Facets never own files. Every mutation streams to the
supervisor through a credit pool, so a parallel `npm install` can't flood the
DO. Heavy staging stays outside too. I assemble opencode's ~20 MB module map
outside the DO because assembling it inside crossed the memory cap and reset
the session. I learned that from a live run.

## The numbers I design against

| Constraint | Cloudflare's figure | What it produced |
|---|---|---|
| Isolate memory | 128 MiB each | multi-isolate processes; staged module maps |
| DO SQLite storage | 10 GB per object | the session disk |
| CPU per invocation | 30 s default, 5 min via `limits.cpu_ms` | phased git clone, sliced checkout, fan-out installs |

A raised `cpu_ms` applies to the supervisor. Facets keep ~30 s, so long
facet work must be split into phases. When the DO hibernates, its disk stays.

## Trust

Isolation is deliberately boring. Nimbus inherits workerd's isolation —
the same primitives Cloudflare runs untrusted customer code on. The CSP allows no
runtime `eval` or request-time WASM compilation. Sessions share only read-only,
content-addressed caches, and loopback stays inside a session. Outbound access
is open by default because npm and git need it. Per-session egress policy is an
honest gap on the [research page](/docs/fine-print/research/).
