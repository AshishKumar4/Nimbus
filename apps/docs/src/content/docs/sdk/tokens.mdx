```ts
import { issueNimbusToken } from '@nimbus-sh/sdk';

const token = await issueNimbusToken(env, {
  tn: 'acme',                 // tenant (required)
  sub: 'alice',               // subject within the tenant
  scopes: ['sandbox:use'],    // grants; absent = all permitted
  sid: 'job-123',             // pin the token to one session
});
```

Auth is deliberately simple: HS256 JWTs signed with `JWT_SECRET`, pure
WebCrypto, no external IdP, no dependencies. The verifier never reads
`alg` from the token header, which kills the `alg: "none"` confusion
class outright (RFC 8725 §3.1). Scopes, tenant and session pins, and
destroy permissions are enforced server-side; client checks are only a
convenience.

v1 honors six scopes: `session:create`, `session:attach`,
`session:bootstrap`, `session:destroy`, `session:admin`, `sandbox:use`.
Default TTL is 1 hour, the maximum is 30 days (larger throws
`E_TOKEN_TTL_TOO_LARGE`). To rotate secrets, set `JWT_SECRET_PREVIOUS`
next to the new `JWT_SECRET` — verification accepts either, issuing uses
the primary — then drop the old one after the longest TTL passes.

## How a browser session gets authorized

Long-lived tokens travel only in `Authorization: Bearer` headers, never
in URLs. The one URL-carried credential is the attach exchange:

1. `POST /new` (with `session:create`) redirects to an attach URL
   carrying a 90-second, single-use, `session:bootstrap` token. Its `jti`
   is consumed set-if-absent in the session DO; a replay gets `401`.
2. The session shell trades it for a sid-pinned `session:attach` cookie
   (`HttpOnly`, `Secure`, `SameSite=None`, `Partitioned`) and redirects
   to the clean URL, so the token never lingers in history.
3. HTML, WebSocket, and API requests all ride that cookie.

```ts
import { sessionAttachUrl, issueNimbusToken } from '@nimbus-sh/sdk';

const url = sessionAttachUrl('https://my-nimbus.workers.dev', 'pretty-otter-1234', token);
// → https://my-nimbus.workers.dev/s/pretty-otter-1234/?nimbus_token=eyJ…
```

One known limit: the exchange stores one sid-pinned cookie per browser
partition, so two Nimbus iframes on the same page evict each other's
cookie. Concurrent multi-session embeds need a per-session cookie design;
that's a tracked follow-up.

Auth failures are typed — `NimbusTokenExpiredError`,
`NimbusTokenSignatureError`, `NimbusAuthConfigError`, and friends — never
stringly.
