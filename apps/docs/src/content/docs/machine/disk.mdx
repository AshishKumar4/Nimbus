---
title: The disk
description: 10 GB of SQLite-backed storage that survives everything short of deleting the session.
---

Everything you write lands on a 10 GB SQLite-backed disk owned by your
session's Durable Object, and it survives WebSocket drops, browser
restarts, hibernation, and DO eviction. That's the one non-negotiable in
the design: facets die, sockets drop, the disk stays.

```bash
$ echo "still here tomorrow" > /home/user/note.txt
# close the tab, come back next week
$ cat note.txt
still here tomorrow
```

What's real on it: binary-safe round trips (`fs.writeFileSync` with
arbitrary bytes is probed behavior), symlinks and stat metadata, a durable
exec bit that `chmod +x` persists and `./prog` honors, and file watching —
the editor and dev servers get coalesced change events from the VFS event
bus, which is part of why Vite HMR works. Every path also carries a
revision watermark, so runtime caches invalidate precisely instead of
guessing.

Every side of the machine sees the same bytes. The shell, all four
runtimes — a compiled C program's `fopen("./data.txt", "r")` reads what
`cat` sees — the browser editor, `box.files` in the SDK, and the agent's
tools.

Writes from processes stream back to the supervisor through a credit
pool: no credits, no send. That mechanism is what lets a parallel
`npm install` or an 84,000-file checkout land inside a 128 MiB isolate.
`fsync` and process exit are durability boundaries; hibernation never
loses a committed write.

One honest nuance. For speed, short-lived runtime paths read from bounded
snapshots (revision-invalidated) rather than the live bridge, and
long-running processes increasingly use the live bridge. The rule the
implementation converges on: you read either the latest committed state
or your own unflushed write. [Inside the disk](/docs/internals/disk/) has
the machinery.
